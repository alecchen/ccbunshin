# Shell completion

`ccbunshin completion <bash|zsh>` prints a completion script generated by the
binary, so the offered words cannot drift from the CLI, and profile names are
read at completion time.

## Sub-features

- `completion-bash` offers the top-level commands, `proxy` subcommands, `init`
  shells, and live profile names.
- `completion-zsh` registers completions through both activation paths: the file
  on `fpath` (ccbunshin only) and a `source` line (ccbunshin and `claude`).
- `completion-claude` completes Claude Code's common options for the wrapper.
- `completion-live` reflects profiles created after the script was generated.

## How to get to it (user POV)

- Run `ccbunshin completion bash > ~/.ccbunshin-completion.bash` and source it
  from `~/.bashrc`.
- Run `ccbunshin completion zsh > ~/.ccbunshin-completion.zsh` and source it
  from `~/.zshrc` after `compinit`.
- Or put the zsh script on `$fpath` as `_ccbunshin`.

## Driving it with the sandbox

Preconditions:

- Two profiles exist, `provider1` and `provider2`.
- `bash` and `zsh` are on `PATH`.

- **Generated, not shipped.** `ccbunshin completion bash > "$VERIFY_DIR/c.bash"`
  and `ccbunshin completion zsh > "$VERIFY_DIR/_ccbunshin"`. Both exit 0 and
  both parse: `bash -n "$VERIFY_DIR/c.bash"`, `zsh -n "$VERIFY_DIR/_ccbunshin"`.
- **Bash words.** In `bash --noprofile --norc`: `source "$VERIFY_DIR/c.bash"
  COMP_WORDS=(ccbunshin ""); COMP_CWORD=1; _ccbunshin; printf '%s\n'"${COMPREPLY[@]}"` -H`.
  The output contains `init`, `launch`, `proxy`, `completion`, `uninstall`,
  `version`, `help`.
- **Bash subcommand and profiles.** The same call with
  `COMP_WORDS=(ccbunshin proxy "")` offers `init start stop restart status`;
  with `COMP_WORDS=(ccbunshin launch "")` it offers `provider1` and `provider2`.
- **zsh, fpath path.** With `fpath=($VERIFY_DIR $fpath)` and `compinit`,
  `zsh -f` reports `ccbunshin=_ccbunshin` and `claude=` empty: `compinit` reads
  only the leading `#compdef` line.
- **zsh, source path.** After `autoload -Uz compinit; compinit` then
  `source "$VERIFY_DIR/_ccbunshin"`, both `ccbunshin=_ccbunshin` and
  `claude=_claude` are registered.
- **Live profiles.** Create `provider3` after the script was generated, then
  repeat the bash profile call. `provider3` is offered without regenerating.
- **Proof.** Capture the two generated scripts, the parsing exit codes, and the
  word lists under `$VERIFY_DIR/artifacts/completion/`.
- **Whole suite.** `sh tests/completion-test.sh` builds its own binary and drives
  all of the above; run it before hand-driving the pieces.

## Gotchas

- The script is generated by the binary under test. A system-wide `ccbunshin`
  earlier on `PATH` produces a script for the wrong version; check
  `command -v ccbunshin` points into `$VERIFY_BIN`.
- `compinit` caches its scan; a stale `~/.zcompdump` can hide a newly added
  script. Pass `-d` a scratch dump file, as `tests/completion-test.sh` does.
- On macOS a terminal `bash` is a login shell that reads `~/.bash_profile`, not
  `~/.bashrc`. That affects installation, not generation, but a manual
  completion test that sources `.bashrc` will appear to do nothing.
- `ccbunshin init` does not install completion scripts; nothing is installed for
  the user, and no directory has to be created.
